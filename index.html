01 / The change in one picture

Declare axis meaning at the point of creation.

A tensor supplies geometry. It does not label its dimensions. The new registration hook carries a separate, typed declaration of those labels.

What is added

KVCacheAxis, KVCacheTensorLayout, an optional registration hook, standard view declarations, runner propagation and MultiConnector forwarding.

What stays authoritative

The actual tensor's shape, strides, dtype and storage offset. Cache specs own content encoding and state granularity.

What is not completed

Hardware-plugin adoption, LMCache consumption, a versioned MP schema, arbitrary component roles, or conversion between incompatible encodings.

Scope: registration-time metadata. This PR does not transpose tensors, change attention kernels, or claim a throughput improvement.

02 / The motivating correctness problem

At two blocks, shape and strides cannot tell K from V.

RBLN has two legitimate views: custom kernels use [B,2,H,1,N,D]; the Triton path uses [2,B,H,1,N,D]. When B=2, the shape and contiguous strides are identical. A detector can choose an interpretation, but cannot recover the producer's intent.

Figure 2 · Interactive ambiguity, using the same physical values
Identical shape and strides

Illustration: H=1, N=2, D=1; scalar values are physical offsets. Color means the declared component, not information stored in the bytes.

Blocks first

BLOCKKVHEAD1STATEHEAD_DIM

K/V first

KVBLOCKHEAD1STATEHEAD_DIM

Canonical output is independently ordered by component, then block and state. At B=2, identical input geometry produces different K/V sequences. At B=3 these two shapes differ, but that does not turn arbitrary shapes into semantic declarations.

Why round-trip tests can miss this: saving with the wrong interpretation and restoring with the same wrong interpretation may reconstruct the original buffer. Comparing independently expected K and V sequences catches the semantic error.

LMCache #5748 adds support for both RBLN formats and addresses a concrete deployment regression. The two-block ambiguity explains why a durable producer contract is still valuable after that detector fix.

03 / Vocabulary that prevents review confusion

“Layout” covers three separate contracts.

Figure 3 · Meaning, address, content

1 · Axis semantics — what does each index mean?

BLOCKHEADSTATECONTENT

KVCacheTensorLayout.axes describes tensor indexing order. Added by this PR. It does not sort axes by strides or decode CONTENT.

+

2 · Physical geometry — where are the bytes?

shape + stride + dtype + storage_offset + storage. Existing KVCacheLayout selects physical permutations such as LBHNC and LBNHC. A block need not be a dense, contiguous span.

+

3 · Content / state semantics — what is stored there?

KVCacheSpec and backend contracts define packing, head slots, quantization, latent/recurrent content and tokens per stored state. This PR does not serialize all of that information.

NameMeaning hereDo not assume
KVCacheAxis.KVExplicit two-way selector: K at 0, V at 1.Not number of caches; not an MLA latent-count axis.

CONTENT / COpaque payload per head slot and state.No implicit K/V split or quantization encoding.

04 / Same axis roles, different memory order

The standard view stays BHNC. Its strides can change.

The common allocator creates a logical [L,B,H,N,C] view, then selects each layer to expose [B,H,N,C]. Physical permutations and page padding are expressed through strides and offsets, not by relabeling the public indices.

Figure 4 · Two physical orders for the same indexing contract

LBHNC

Within one layer and block, heads precede states.

H0 N0H0 N1H1 N0H1 N1
cache[b,h,n,c]

LBNHC

Within one layer and block, states precede heads.

N0 H0N0 H1N1 H0N1 H1
cache[b,h,n,c]
ExamplePer-layer shapePer-layer strides in elementsAxis tuple
LBHNC[8,4,16,128][8192,2048,128,1](BLOCK,HEAD,STATE,CONTENT)
LBNHC[8,4,16,128][8192,128,512,1]

The small colored strips are illustrative H/N cells; the numeric table uses B=8, H=4, N=16, C=128. Neither strip implies that all backends support both orders.

address(b,h,n,c) = storage_base + element_size × (
    storage_offset + b·stride_B + h·stride_H + n·stride_N + c·stride_C
)

Tensor strides and storage_offset are in elements; allocator planning may use byte strides. Convert units explicitly. Axis metadata supplies the meaning of B/H/N/C, not the numbers in this address formula.

08 / Layers, aliases and hybrid models
A layer map is not a promise of one layout, one allocation or one encoding.


Figure 8 · Shared backing does not erase per-layer views
The drawing illustrates cross-layer physical packing. Hybrid cache groups can additionally overlay storage according to the allocator plan; independent layer keys do not imply independent buffers.


Registered view, illustrativeAxis rolesAdditional interpretation needed
Full attention [B,8,16,C₁]BHNCDense K/V packing and dtype.
Sliding attention [B,8,16,C₂]BHNCIts retention/group/block-table policy and spec.
Compressed MLA [B,1,4,C₃]BHNCLatent encoding and tokens per stored state.
Recurrent / Mamba [B,1,1,C₄]BHNC for the standard viewState components, component dtypes and payload organization.
Raw self-managed backingNo entryIts owner's explicit contract; no default axes assumed.


Hybrid correctness requires more than axes: combine the per-layer declaration with the actual tensor, matching cache spec/group information and block/state interpretation. This PR does not make all layers interchangeable.


Attention binding can create kernel-block views after allocation. The connector receives the registered allocation view and its matching descriptor, not an axis tuple copied from a backend-private view. A BLOCK label alone does not define how its indices map to scheduler blocks; specs and block mapping still matter.

10 / A size-one dimension is not automatically a KV dimension
MLA has no separate K/V selector in its standard view.


The descriptor's KV role means two separately addressable components, K then V. MLA's shared latent representation does not become a one-element K/V selector. MLAAttentionSpec sets head_size_v=0; its content is interpreted through the spec.


Figure 10 · Three valid MLA declarations
Standard view
[B,1,N,C]
BLOCKHEADSTATECONTENT
Size one is a head slot. Keep its semantic role.
Custom squeezed view
[B,N,C]
BLOCKSTATECONTENT
No head or K/V axis is required by the descriptor.
Custom padded rank
[1,B,N,C]
SINGLETONBLOCKSTATECONTENT
Use SINGLETON for an actual placeholder, not a semantic axis.


Invalid declaration: describing [1,B,N,C] as (KV,BLOCK,STATE,CONTENT) raises ValueError. A lone element does not identify K, V or latent content. Relaxing the size check would introduce ambiguity rather than encode MLA.


validate_shape checks rank, KV size two and SINGLETON size one. Construction rejects duplicate named roles except SINGLETON. These checks do not prove a declaration is true: equal-sized axes can still be mislabeled. Correctness starts with the producer's known view contract.

A missing entry means unspecified semantics, not an implied default. The base hook allows partial mappings. A consumer requiring complete explicit semantics must reject unsupported/missing entries or use a well-defined, spec-aware legacy path. Overrides are responsible for validation before consumption.


Important scope boundary: #63699 alone does not make an existing LMCache connector stop detecting formats. It must implement the new hook and carry the declaration through its own adapters and registration transport.

12 / Intended end state, beyond this PR
Declare → preserve → validate → resolve once → transfer.


Figure 12 · The complete producer-to-consumer contract
Producer owns the truth
Actual registered tensors + axis declarations + matching cache-spec/group context. Standard allocator or custom plugin; descriptors follow the exposed view.
↓
vLLM registration boundary
Runner → typed hook → optional MultiConnector → child. This transport inside the engine is provided by #63699.
↓
Consumer adapter & MP registration
Future LMCache work: forward semantics through normalization and REGISTER_KV_CACHE; define a versioned transport schema, explicit component roles and required encoding/granularity context. Python IntEnum values alone are not a wire protocol.
↓
Validate and retain a supported format
Future: map declarations plus specs/geometry to supported EngineKVFormat/KVFormatSpec and group/transfer behavior. Explicit inconsistent or unsupported metadata should fail clearly, not be replaced by a guess.
↓
Use existing execution paths where compatible
Future: transfer with the right address geometry and kernels. Preserve matching metadata on restore, reallocation and cross-process handoff. Negotiate or reject incompatible encodings rather than promise universal conversion.
Blue: producer/API work in this PR. Dashed amber: proposed consumer integration and broader contract work tracked by LMCache RFC #5866; not implemented or validated by #63699.


Explicit path
Producer declaration is authoritative. Consumer validates it against the exact view, retains the result, and dispatches without re-guessing axis roles on each use.
Legacy path
Keep support for older engines when interpretation is supported and unambiguous. Ambiguous cases require more information; an unrelated device-name default is not proof.

13 / What is lost when the declaration is absent
A wrong axis interpretation can become a wrong byte selection.


Figure 13 · A possible failure chain, not a claimed production incident
Unlabeled viewConsumer sees shape and strides.
→
Ambiguous detectorTwo supported interpretations fit.
→
Wrong geometryBlock/KV role or component split is wrong.
→
Wrong bytes transferredCanonical chunks can contain mismatched K/V sequences.


Visible rejection
A new producer layout may be refused as unsupported. RBLN blocks-first support in LMCache #5748 addresses such a concrete integration regression.
Silent ambiguity
Equal-sized axes can pass shape and bounds checks. Canonical-value tests demonstrate the risk; this guide does not claim an observed production output failure.
Maintenance coupling
Every producer shape change can require a new consumer heuristic, even though the producer already knows the intended interpretation.


Not every tensor-only integration is unsafe. Existing spec-aware contracts can be precise, and many layouts are unambiguous. The issue is treating geometry or backend names as a complete semantic contract when they are not.

14 / Metadata must follow the view's lifecycle
Carry the tensor and its declaration as one logical pair.


Figure 14 · Transformations that need matching semantics
EventTensor changeDescriptor / context action
Permutation[B,H,N,C] → [B,N,H,C]Permute axes to (BLOCK,STATE,HEAD,CONTENT).
Squeeze a head slot[B,1,N,C] → [B,N,C]Remove HEAD from this exposed view. Do not leave a rank-four declaration.
Shared-layer aliasNew layer key points at the same tensor.Copy the target declaration under the alias key. Implemented in both runners.
Component split / reshapeOne payload becomes multiple views, or dimensions are merged.Describe new view roles and component identity; axis permutation alone may be insufficient. Broader schemas remain follow-up.
Reallocation / recoveryNew storage or different views.Re-register new matching tensor/descriptor pairs; do not rely on stale addresses or cached metadata.
Cross-process handoffPython objects cannot be passed unchanged.Serialize a versioned, consumer-understood contract; preserve dtype/spec/state context and reject unsupported versions.


Declaring a view once helps only if later adapters preserve its semantics. Reinterpreting, squeezing or regrouping the tensor while retaining old axis labels recreates the original problem.

16 / A practical review route
Review the contract before the plumbing.


  1. 1. Types and validation. Is the distinction between KV selector, HEAD, STATE and opaque CONTENT clear? Does validation reject impossible fixed-size axes without pretending to prove semantics?
  2. 2. View creation. Are declarations attached where the actual BHNC view is created? Are raw-storage paths omitted?
  3. 3. Runner propagation. Follow the fresh output map through standard/HiSparse allocation and shared aliases. Verify registration describes the connector view.
  4. 4. Compatibility. Does inherited registration preserve existing overrides? Does MultiConnector pass the same semantics to all children?
  5. 5. Behavior tests. Compare independently expected K/V values, tensor identity, strides, mixed specs, aliases and error handling.
  6. 6. Downstream boundary. Check that RBLN uses the shared upstream contract, while LMCache consumer/MP work remains explicitly out of scope.
